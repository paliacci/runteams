# 对话内容展示

先回答用户最想知道的结论，再用最容易看懂的形式提供依据。多个对象都需要说明相同维度（如依据、限制、建议）时，先用紧凑表格供人比较，共通解释放表外，必要细节再展开，避免给每个对象重复写一大组小标题。组件服务于内容，不是每次回复的固定模板，也不是工作量证明。不要向用户询问要不要表格或图表来转交本应自行完成的判断。

- **文字**：解释、建议、单个事实或简单进度，直接说清即可。几项短信息可用普通列表，不为使用组件凑出表格。
- **数据表格**：多个对象按同一组字段比较、或展示结构化记录时使用产品 `table`，获得统一的样式、搜索、排序和详情，不用大段 Markdown 表格代替。只保留影响判断的列，列名说人话；内部编号确需追踪时单列，不混入名称。每格只放一个短标签或关键事实，依据与限制需要完整解释时放在表外，不把几段分析塞入一个格子。
- **数值图表**：真实数据中的大小、分布或差异用 `chart`。当前支持横向条形图，不声称支持折线、饼图或任意可执行网页。几行已十分清楚的数据不必再重复画图；图表自带数据表，不另复制同一表格。
- **交互筛选**：确实需要用户自行按类别和非负数值下限探索一组记录时使用 `explorer`。它是本次回复的本地筛选，不是可写数据库或业务操作。

需要组件时先读 [内容协议](references/protocol.md)，然后在**最终回复正文**里输出 `runteams-view` 围栏，与普通文字自然穿插；不要只写到文件或放进工具输出。样式和交互由产品统一负责，无需生成 HTML、CSS、JavaScript 或自行设计颜色。

数据来自本次已核实资料或明确标注的示例，不能为凑图编造、把未知填成 0、拿样本当整体。数值、单位、时间窗口、样本范围要能核对；必要来源用正文中的真实可访问链接说明。短结论不丢失会改变判断的重要限制。多个可切换指标采用涵盖所有指标的标题，单位不一致的指标分开呈现；缺失数据用 null，不能画成测得的零。

发送前核对：首句是否回答问题；组件是否真的降低阅读负担；表内与文字数值是否一致；是否误把推测当事实；格式是否满足协议。超过组件容量时精选与问题相关的数据，明确筛选范围并引用已有完整成果，不静默截断。

回复随对话保存，不等于已保存为文档、已入库或已完成业务动作。需要正式汇报时按 `runteams-work-report` 保存同一工作的成果；对话只说明关键结论和入口，必要时展示有助判断的数据，不在两处重复维护整份成果。文档块协议与本技能不同，不能把消息围栏当文档结构提交。用户要求直接在对话中交付时直接回复。
