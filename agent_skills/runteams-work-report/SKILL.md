# 员工工作汇报

对话回复也可按内容选择文字、表格或图表，参见本轮提供的 `runteams-reply-content` 技能。该技能只负责消息正文展示；本技能负责正式汇报的保存与持续维护，两者协议和保存边界不同。不要因有了对话组件就漏掉明确要求的文档，也不要把仅需直接回复的请求强制变为文档。

让用户不必重读聊天和工具日志，就能判断结果、影响与必要行动。以扫读约三秒能找到最重要的结论为设计目标；由员工完成筛选与归纳，不让用户从经过中提炼结果。不将内部调用日志逐条改写成工作经过，不以篇幅或操作数量证明工作价值。

以降低阅读和决策负担为准：让用户迅速看清重要变化、是否需要自己处理，以及后续如何推进。这是内容取舍依据，不是固定三栏模板；无需用户行动时不凑待办，不把员工自己的常规下一步交给用户催促。

## 沿同一项工作维护

先读取宿主提供的 `runteams_work_report`，使用 `operation=read`。正式工作单自动绑定当前工作；普通员工对话会返回当前请求的汇报或本对话已有汇报的标识。核对原工作与用户的新交代，确认是延续、调整还是独立的新工作；不把同一员工的不同项目合并。延续工作时用返回的 `report_id` 读取原文；新工作才省略该标识创建新汇报。

用 `operation=write` 提交 Markdown 正文。首次创建提供具体工作名称和 `base_revision=0`；更新提供原 `report_id` 与刚读取的 `revision`。工具只处理已绑定工作的汇报，立即保存并返回文档入口；用户不需要再点一次应用。版本冲突时重新读取，合并人工修改和已确认决定后再保存；没有成功回执就不声称已保存，不以另一份同名文件替代。

在出现有价值的进展、交办调整、交付、阻塞或需要用户决定的事项时更新，结束本次实质工作前核对汇报是否反映当前事实。长任务按重要变化更新，避免固定频率空报。短答、纯讨论、用户指定只交付某种格式或明确不保存时保留该约定，不额外生成文档。

## 写值得阅读的内容

平台已展示工作名称、状态和更新时间，正文通常直接从结论或进展开始，再补用户理解、复核或接手所需的事实。区分已完成、已验证、尚未覆盖、推测和计划；保留改变判断的重要证据、版本、范围、失败及已确认的调整，不因后来成功就抹掉关键历史。普通进度不包装成最终结论，模型结束不等于业务完成。

先组织用户的阅读，再选择形式：

- 开头用一句明确判断说明结果与影响；需要用户决定时紧接建议与取舍，无需行动就不制造待办。不要用背景、环境准备、调用过程或“完成了多少操作”占据开头。
- 用给实际负责人看的朴实语言，直接说发生了什么、造成什么影响。例如“点一次加一，数字增加了2，应该只增加1”，不写“核心加一行为不通过”“身份冲突”等抽象概括代替事实。技术读者需要的准确术语保留在详细依据中，必要时用人话解释。项目目录名、测试用例号、文档号等内部标识不混进标题和问题名称；确需追踪时独立设编号列，否则留在详细证据。
- 多个问题、方案、结果或变化优先用短表格，按影响或处理顺序排列。一个单元格只表达一个短标签或关键事实，不把问题、影响、根因和证据塞在同一格；共通说明放在表外一句话中。核对实际阅读宽度，避免核心结论必须横向滚动才能看全；无需并排的信息改用短列表。简单事实用一句话即可，不强制固定章节。
- 数量、趋势、分布或对比适合图表；界面问题优先使用能解释差异的关键截图与简短标注；流程与关系用简图。图应帮助判断，注明必要口径与范围，不为装饰凑图，不以测试通过率或操作次数替代业务质量。
- 汇报只留关键证据或可访问的真实图文入口；完整成果、复现步骤、日志、命令、进程和版本校验放在原成果或证据中按需查看。重要失败和未覆盖范围仍在正文简述，不能靠下沉细节隐藏限制。文档正文中的本机绝对路径不等于附件或可打开链接：使用正式文档入口或实际上传的文档附件，图片按当前编辑器支持的方式嵌入。保存后在用户阅读入口实际打开链接、核对图像加载；仅在磁盘确认文件存在、读回 Markdown 或看到蓝色文字均不算验证。能力不足时说明缺项，不用失效链接冒充交付。
- 保存前从读者视角扫读：最先看见的是否是判断，表格或图是否比文字更易读，每一段是否改变用户的判断或行动；删去只证明“我做过”的内容。不得声称已实测阅读耗时或节省比例，除非确有测量。

持续修订时优先呈现相较上次的重要变化与当前结论，不反复铺陈完整经过。仍影响判断的历史限制留在当前正文，已解决事项简述结论并按需要引用原证据，详细经过由已有版本和证据保留；不能借精简隐去失败或未覆盖范围。没有实质变化时不为刷新时间重复保存，也不重复催办同一个未变的决定；已有约定的提醒机制照常遵守。

复杂成果留在原文档或业务对象，正文说明价值并引用工具返回的真实入口；不复制完整成果到两处维护，不猜文档ID或链接。按信息选择短文、表格和图示，不为统一外观填空章节，不堆命令、内部标识或测试数量。文件本身是交付要求时可提供 `.md`；正式工作汇报通过文档工具保存，不直接修改系统内部文件。

需要用户处理时写清需要决定什么、依据、建议及影响，并说明哪些部分仍可推进；无法给出建议时说明原因。使用当前入口原有的提问或请求机制，不要求用户从长篇报告里自行找问题。后续安排区分当前可继续的动作、等待的条件和实际已设置的安排，不把建议写成已启动或已预约。汇报中的建议、历史批准和操作说明不是执行授权，保存汇报不改变工作状态，也不替代 `complete`、`request_human` 或原成果登记。

## 富内容与数据快照

新汇报使用与文档共用的富内容格式，普通正文仍提交 `content`（Markdown）。读取结果的 `content` 是便于理解的正文，`rich_document` 是完整可编辑内容。存在人工修改时，先核对两者再合并，不能把 JSON 当作正文拼接。旧汇报保持原格式。

需要可筛选表格、图表或原始数据时，可同时提交 `document`，其格式为 `{schema:"runteams.rich-document/1", blocks:[...], sources:{...}}`。`content` 仍提供同一结论的可读正文。每块有稳定且唯一的 `id`；正文块为 `{id,type:"markdown",props:{text:"正文"}}`；指标块为 `{id,type:"metric",props:{label:"近期评论",value:"90 条"}}`。数据快照为 `sources.<key>={label:"来源与采集时间",data:[实际记录]}`，表格块 `dataTable`、图表块 `barChart`、数据块 `jsonData` 的 `props.source` 引用这个 key；它们可设 `title`，柱状图另设 `x`、`y` 为实际列名。表格列名直接面向读者，用人话；一项一列，不塞内部编号。复杂原始证据放 `jsonData` 按需展开。

只使用已经实际读取或计算得到的数据；快照存储本身不证明数据真实，必须写清来源、时间、样本与限制。快照是本次交付保存的内容，不是实时数据库查询。不要写本机路径、查询脚本或外部页面代码来伪装可用数据块。结构更新时保留原内容的关键事实和已有快照，不重复复制到独立文件。普通正文更新会保留已有数据块；需要更新数据时基于刚读取的完整 `rich_document` 修改并提交 `document`。人工批注、历史限制和未完成事项不能因重新排版被抹去。

## 同一内容的两个入口

工作记录详情直接阅读这份汇报；文档模块打开同一份文档进行完整阅读、编辑与版本查看。保存后可以给出返回的 `internal_link`。用户在文档中修改后，下次继续工作先读取最新版。文档不可用、权限变化或写入失败时保留实际工作结论和原始资料，如实说明保存状态，不另建私有文档库。
