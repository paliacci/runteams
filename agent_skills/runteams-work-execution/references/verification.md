# 按产物核验与交付

## 结论与证据

先确定这次交付中哪些重要结论需要证明，再选择能检验它们的实际方法。检查结果必须对应当前产物或能确认未变化的版本与条件；既有证据适用时可复用，不为了每句话重复执行相同检查。

核对实际结果、失败项与检查范围。测试通过不能单独证明全部需求满足，构建成功不能证明业务上线，工具受理不能证明外部操作完成，另一名 Agent 的自述不能替代可核实的产物或回执。证据不足时缩小结论或说明未验证，不自动把证据不足判为产物失败。

## 根据工作选择方法

| 产物或工作 | 合适的核对依据 | 不能单独证明什么 |
| --- | --- | --- |
| 软件与可操作界面 | 对照原问题和需求检查受影响行为，读取相关测试、构建或实际操作结果 | 测试数量不能证明全部业务完成；截图不能单独证明交互有效 |
| 数据分析与研究 | 核对来源、时间、统计口径、计算、引用与不确定性，抽查或复算关键结论 | 来源数量不能证明结论正确；推断不能写成已证事实 |
| 文章、设计等主观产物 | 对照用户目标、项目语气、事实与交付要求审阅；需要时请用户评价 | 固定评分、报告篇幅或工具输出不能证明用户满意 |
| 提问式辅导或协作讨论 | 核对是否遵守约定、问题是否有效、已观察到什么理解或决定 | 直接给出最终答案不能代替用户要求的辅导过程；单轮不能证明已掌握 |
| 外部业务操作 | 核对原请求身份、当前回执与实际业务状态 | 请求已发送或本地文件存在不能证明业务成功 |

按具体任务使用其中相关依据，不要求每项工作涵盖全部类别。遵守已有正式检验合同；修正后复查受影响部分，只有新变化、失败或未解决问题需要时才扩大或重复检查。

## 保留岗位约定

验证可以在内部进行，交付仍遵循 soul 与本轮要求：JSON 岗位继续返回指定结构，文章岗位交正文与所需引用，辅导岗位保持提问式协作，不额外生成验收报告。必须表达的范围和不确定性通过允许的格式或当前入口呈现，不编造成果链接。

不规定固定修订轮次，不默认首版失败，不强制所有产物截图或运行命令，也不无依据承诺生产可用。记录与结论相称的证据即可，完整日志留在已有证据入口，不让用户重复整理平台已有记录。

“完成结论须有对应证据”的思路借鉴 [Superpowers verification-before-completion](https://github.com/obra/superpowers/blob/main/skills/verification-before-completion/SKILL.md)，这里按岗位和产物适配，不引入其所有工程流程或命令要求。
