# 文档协作

RunTeams 的文档系统保存用户需要独立阅读、编辑或分享的成果，例如分析、方案和总结。结构化问题、状态、操作与执行证据使用对应结果记录和任务，不因挂载本技能就必须写文档。挂载后，员工协议提供三个工具：
`list_documents`、`get_document`、`write_document`。

文档由产品自己的结构化内容存储保存，工具负责归属、授权和版本检查。员工用 Markdown 交换正文；
表格、任务清单、代码、公式、Mermaid 和图片均可写入。不要直接访问数据库或工作区文件来绕过工具。
用户在文档编辑器里的修改和排版也会生成修订，更新前必须重新读取。

## 协作完成可读文档

先确定文档的读者、要解决的问题、已有事实和必要的使用场景；已有信息足够时直接写，不要求用户按固定问卷重复提供背景。将确定事实、推测和未决事项区分，把关键结论放在前面，再给出读者需要的依据和可执行步骤。

用户要精炼方案或简报时，交付读者能直接使用的短文：合并重复事实、条件和限制，通常以结论、行动、验收与失败处理、待确认项组织，不自动扩成完整治理手册。完整检查记录保留在运行证据，不复制进正文。只有用户要求详细制度或复杂场景确有需要时才扩展章节。

用户只提供验收项数量、预算状态等概括事实时，保留该事实；不得自行补造未提供的逐项标准或金额，再写成已经确认的执行门槛。具体清单缺失应在必要的待确认项中说明。如果提出建议，明确标为建议，且不让建议掩盖任务要求或占据正文的大部分。

按实际需要组织内容，逐项检查是否回答读者的问题。复杂文档可请当前渠道可用的独立评审只读核对；没有独立评审能力时自己以读者视角检查，并如实说明。至少核对一项读者可能据此执行的具体动作：所需条件、责任和失败处理是否清楚。发现矛盾或缺少关键事实，修正可修正部分并保留必要限制；不要通过增加篇幅掩盖信息缺口。

这是 RunTeams 独立编写的文档工作方法，与现有文档归属、修订及交付协议整合。公开 `doc-coauthoring` 来源和固定版本仅记录在 `upstream-sources.json`；因该版本缺少明确许可证，未打包其原文，也不宣称是已授权的官方技能包。

## 读取参考资料

- 工作单 `inputs` 或正文里出现的 `runteams://document/<id>` 是用户提供的参考文档（PRD、设计文档、接口约定等）。先用 `get_document` 的 `document_id` 读取全文，再开始工作。
- 读不到（不存在或已删除）时，把它列为缺失的输入，不要猜测文档内容。
- 参考文档是判定依据，不要修改它；发现规格与实际冲突时，在交付中列为“需要确认”。

## 长期文档与单次交付物

| | 长期文档 | 单次交付物 |
|---|---|---|
| 用途 | 跨多次运行维护的可读内容：方案、说明、知识库 | 这一次运行的成果：报告、方案、清单 |
| 写法 | `write_document` 提交合并后的 Markdown，服务按块更新，每次形成一个新版本 | 写进工作区文件，由本技能 work 的交付声明登记 |
| 历史 | 由文档版本保存，正文不追加过程 | 每次运行各自一份 |

不要把单次运行的过程叙述写进长期文档，也不要每次运行都新建一份工作区文件来代替长期文档。

## 维护长期文档

1. **稳定的 key**：`document_key` 由对象身份决定，同一对象永远用同一个 key，例如 `project-guide-<项目稳定标识>`。不要包含日期、运行序号或本机路径。
2. **先读后写**：用 `list_documents` 找到自己的文档，用 `get_document` 读出正文和 `revision`。
3. **只保存当前状态**：正文是“现在是什么样”，例如头部摘要加状态表。过程、简短运行结论写进任务结果，证据登记为附件。
4. **带版本写回**：更新已有文档时，`base_revision` 必须等于刚读到的 `revision`。版本冲突说明别人（通常是用户）刚改过：重新读取，保留对方的改动后再合并写入。
5. **尊重用户的修订**：用户在文档里做的标注（例如标记误报、不处理、忽略规则）是指令，必须保留并照做，不得覆盖或回退。
6. **没有变化就不写**：内容与当前版本相同时不要写入，避免产生空版本。
7. **局部更新**：只改需要维护的段落、条目或表格内容；其余正文原样保留。工具会保留未变化块的身份、排版和标注，不要为了统一风格重写整份文档。Markdown 不包含的颜色、对齐等排版由内核保存，不要自行抹掉。
8. **引用其他文档**：用 `get_document` 返回的 `internal_link` 作为 Markdown 链接目标，不要编造文档 ID。

## 安全

- 文档正文不得包含密钥、口令、令牌、凭据或本机绝对路径。
- 只写自己的长期文档；其他员工或用户的文档只读。

## 问题列表

正式问题结果不要求另建文档或绑定台账。已有绑定文档继续兼容 data_view={"kind":"work_items","repository_key":"get_task 中的真实 repository_key"}，保留其身份、人工内容与历史，不能手写另一份状态表。用户需要独立成果时可引用问题链接；处理操作属于结果界面。更新省略 data_view 会保留绑定；传空对象可以解除。标题、正文与绑定统一修订并使用 base_revision。员工仍只可绑定本次授权或交接仓库。

## 保存用途协议

工作合同声明的必交文档由平台登记为 document；额外单次文档通过 publish_artifact 指定 purpose=document 和 document_reason，说明用户独立阅读/编辑/分享的用途。证据指定 purpose=evidence，其余文件默认 attachment。格式只决定阅读器，不决定产出用途；不要把业务状态、问题或工具回执包装为报告。

## 正式工作与代表样例

工作范围和完成标准见 [runteams.json](runteams.json)，代表样例见 [references/work-examples.json](references/work-examples.json)。只把实际执行且读回核对的结果称为工作完成；结构、健康检查和模拟分别记录。
